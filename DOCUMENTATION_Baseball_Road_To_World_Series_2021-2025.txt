================================================================================
 1. OVERVIEW
================================================================================

This workbook contains the complete regular-season and postseason game logs,
plus season-level player statistics, for every team that reached the Major
League Baseball World Series in the five seasons 2021 through 2025 - ten
team-seasons in total (one Champion and one Runner-Up per year).

The data answers the question the visualization explores: what does the road to
a World Series actually look like, game by game, for the two teams that get
there?

Scope
-----
  Seasons covered        : 2021, 2022, 2023, 2024, 2025 (5 seasons)
  Team-seasons covered   : 10 (2 per season - Champion and Runner-Up)
  Regular-season games   : 1,619 team-game rows
  Postseason games       : 161 team-game rows
  Player-season records  : 321 batting, 342 pitching, 426 fielding
  Total data rows        : 2,909 across 6 worksheets

The ten team-seasons
--------------------
  Year  Result      Team                      Tm ID  League  WC Bye
  ----  ----------  ------------------------  -----  ------  ------
  2021  Champion    Atlanta Braves            ATL    NL      TRUE
  2021  Runner-Up   Houston Astros            HOU    AL      TRUE
  2022  Champion    Houston Astros            HOU    AL      TRUE
  2022  Runner-Up   Philadelphia Phillies     PHI    NL      FALSE
  2023  Champion    Texas Rangers             TEX    AL      FALSE
  2023  Runner-Up   Arizona Diamondbacks      ARI    NL      FALSE
  2024  Champion    Los Angeles Dodgers       LAD    NL      TRUE
  2024  Runner-Up   New York Yankees          NYY    AL      TRUE
  2025  Champion    Los Angeles Dodgers       LAD    NL      FALSE
  2025  Runner-Up   Toronto Blue Jays         TOR    AL      TRUE

IMPORTANT - what this dataset is NOT
------------------------------------
This is a *team-centric* dataset, not a league-wide one. It contains rows only
for the 10 World Series participants. Opponent teams appear only as opponent
codes and lookup attributes; their own game logs and player statistics are not
included. Do not use this file to compute league-wide averages or standings.

================================================================================
 3. THE DATA MODEL - HOW THE SHEETS SHOULD BE JOINED
================================================================================

3.1 Shape of the model
----------------------
The model is a star / snowflake. "WS Teams" is the central hub dimension. Four
fact tables hang off it on the single key column "Unique". The two game-level
fact tables each hang a further opponent lookup off their "Opp" column.

                                      +---------------------+
                                  +-->|  Batting Stats      |
                                  |   +---------------------+
                                  |
                                  |   +---------------------+
                                  +-->|  Pitching Stats     |
                                  |   +---------------------+
   +--------------+               |
   |              |               |   +--------------+      +----------------------------+
   |  WS Teams    |---------------+-->|  PS Games    |----->| Team Name Opponite         |
   |  (hub)       |   [Unique]    |   +--------------+      | (instance 1 = "Opponite1") |
   |              |               |        [Opp]            +----------------------------+
   +--------------+               |
                                  |   +--------------+      +----------------------------+
                                  +-->| Season Games |----->| Team Name Opponite         |
                                  |   +--------------+      | (instance 2)               |
                                  |        [Opp]            +----------------------------+
                                  |
                                  |   +---------------------+
                                  +-->|  Fielding Stats     |  (not in the published
                                      +---------------------+   workbook; join it the
                                                                same way)

3.2 The join specification
--------------------------
Six relationships are defined in the published workbook, plus one recommended
seventh for the Fielding Stats sheet.

  #  Left table      Left key      Right table          Right key          Cardinality
  -  --------------  ------------  -------------------  -----------------  ------------
  1  WS Teams        Unique     =  Batting Stats        Unique             one-to-many
  2  WS Teams        Unique     =  Pitching Stats       Unique             one-to-many
  3  WS Teams        Unique     =  PS Games             Unique             one-to-many
  4  WS Teams        Unique     =  Season Games         Unique             one-to-many
  5  PS Games        Opp        =  Team Name Opponite   TeamID Opponite    many-to-one
  6  Season Games    Opp        =  Team Name Opponite   TeamID Opponite    many-to-one
  7  WS Teams        Unique     =  Fielding Stats       Unique             one-to-many
     (recommended; not present in the published workbook)

Relationships 5 and 6 use the SAME lookup sheet but must be two SEPARATE
instances of it. In Tableau the second instance is automatically named
"Team Name Opponite1". In SQL you alias the table twice. Do not try to serve
both game tables from a single joined instance - that would force Season Games
and PS Games onto the same row, which is wrong.

3.3 The join key: "Unique"
--------------------------
"Unique" is the primary key of the whole model. It is a text field built as:

        Year + "_" + League Champion + "_" + Team Name Short

For example:  2021_Champion_Braves
              2024_Runner-Up_Yankees
              2025_Champion_Dodgers

It is deliberately composite because neither Year nor team alone identifies a
row: the Astros appear in both 2021 and 2022, and the Dodgers in both 2024 and
2025. Always join on "Unique" - never on Year + Team Name alone, and never on
the three-letter team code alone.

Key integrity (verified against the file)
  - WS Teams.Unique has 10 values and is unique. Confirmed primary key.
  - Every Unique value in Season Games, PS Games, Batting Stats, Pitching Stats
    and Fielding Stats matches a row in WS Teams. There are ZERO orphan keys.
  - Fielding Stats covers only 8 of the 10 team-seasons (see section 6.8).

3.4 Tableau relationship settings
---------------------------------
If you are rebuilding the model in Tableau, these are the Performance Options
used in the published workbook. They are optional - Tableau infers safe
defaults - but they let the query optimizer skip unnecessary joins.

  Relationships 2, 3, 4 (WS Teams -> Pitching / PS Games / Season Games):
        Cardinality            : One to Many
        Referential Integrity  : All Records Match  (both sides)

  Relationship 1 (WS Teams -> Batting):
        Left at Tableau defaults (Many to Many / Some Records Match).
        Setting it to One-to-Many / All Records Match is safe and is
        recommended for consistency - the data supports it.

  Relationships 5, 6 (game tables -> Team Name Opponite):
        Cardinality            : Many to One
        Referential Integrity  : All Records Match on the lookup side

     >> CAUTION: "All Records Match" on the Opp side is NOT actually true in
        this data. 20 game rows carry an Opp code that is absent from the
        lookup sheet (see section 6.1). With "All Records Match" set, Tableau
        may drop or mis-handle those rows. If you care about those 20 rows,
        either fix the codes first or set Referential Integrity to
        "Some Records Match".

3.5 Critical warning - relationships, not physical joins
--------------------------------------------------------
Use Tableau RELATIONSHIPS (the "noodle" on the logical layer), not physical
inner/left joins, and in SQL do not flatten the whole model into one table.

The five fact tables sit at different grains that share only the team-season
key:

        Season Games    : one row per team per regular-season game
        PS Games        : one row per team per postseason game
        Batting Stats   : one row per player per team-season
        Pitching Stats  : one row per player per team-season
        Fielding Stats  : one row per player per team-season

Physically joining any two of them on "Unique" produces a Cartesian fan-out.
For the 2024 Dodgers alone, joining Season Games (162 rows) to Batting Stats
(23 rows) yields 3,726 rows, and every measure on both sides is then multiplied
- team wins would be counted 23 times and each player's home runs 162 times.

Tableau relationships avoid this by querying each table at its own level of
detail and only combining the aggregated results. If you must work in SQL or
pandas, aggregate each fact table to the "Unique" grain FIRST, then join the
aggregates.

3.6 SQL equivalent
------------------
Treating each sheet as a table of the same name:

    -- Game-level query: regular-season games with opponent attributes
    SELECT  t.[Unique], t.[Year], t.[League Champion], t.[Team Name],
            g.[Gm#], g.[Game Date], g.[W/L], g.[R], g.[RA], g.[Opp],
            o.[Team Name Opponite], o.[League Opponite]
    FROM         [WS Teams]           AS t
    INNER JOIN   [Season Games]       AS g  ON g.[Unique] = t.[Unique]
    LEFT  JOIN   [Team Name Opponite] AS o  ON o.[TeamID Opponite] = g.[Opp];

    -- Game-level query: postseason games (note the SEPARATE lookup alias)
    SELECT  t.[Unique], p.[Series], p.[Post Gm#], p.[W/L], p.[R], p.[RA],
            o2.[Team Name Opponite]
    FROM         [WS Teams]           AS t
    INNER JOIN   [PS Games]           AS p   ON p.[Unique]           = t.[Unique]
    LEFT  JOIN   [Team Name Opponite] AS o2  ON o2.[TeamID Opponite] = p.[Opp];

    -- Combining grains safely: aggregate first, then join
    SELECT  t.[Unique], t.[Team Name], rs.games, rs.wins, b.team_hr
    FROM    [WS Teams] AS t
    LEFT JOIN (SELECT [Unique], COUNT(*) AS games,
                      SUM(CASE WHEN [W/L] LIKE 'W%' THEN 1 ELSE 0 END) AS wins
               FROM [Season Games] GROUP BY [Unique])            AS rs
           ON rs.[Unique] = t.[Unique]
    LEFT JOIN (SELECT [Unique], SUM([HR]) AS team_hr
               FROM [Batting Stats] WHERE [Player] <> 'Team Totals'
               GROUP BY [Unique])                                AS b
           ON b.[Unique] = t.[Unique];

    -- LEFT JOIN is used for the opponent lookup on purpose: 20 rows will not
    -- match (see section 6.1). An INNER JOIN would silently drop them.

3.7 pandas equivalent
---------------------
    import pandas as pd

    xl   = pd.ExcelFile("Data_Baseball_Road_To_World_Series_2021-2025.xlsx")

    # Regular-season games enriched with hub + opponent attributes
    season = (sg.merge(hub, on="Unique", how="left", suffixes=("", "_team"))
                .merge(opp, left_on="Opp", right_on="TeamID Opponite",
                       how="left"))

    # Postseason games - same pattern, independent lookup merge
    post   = (ps.merge(hub, on="Unique", how="left", suffixes=("", "_team"))
                .merge(opp, left_on="Opp", right_on="TeamID Opponite",
                       how="left"))

    # Player tables: keep them separate, or aggregate before joining
    bat_players = bat[bat["Player"] != "Team Totals"]     # drop total rows!
    team_hr     = bat_players.groupby("Unique", as_index=False)["HR"].sum()
    summary     = hub.merge(team_hr, on="Unique", how="left")

================================================================================
 6. DATA QUALITY NOTES AND KNOWN ISSUES
================================================================================

 Everything in this section was verified programmatically against the file.
 None of it prevents the dataset from being used, but anyone building on it
 should know about it. Issues are ordered roughly by how likely they are to
 bite you.

--------------------------------------------------------------------------------
 6.1  Opponent codes that do not match the lookup sheet  (20 rows)
--------------------------------------------------------------------------------
 The Opp -> TeamID Opponite join fails for 20 of the 1,780 game rows. Use a
 LEFT join so these rows survive with null opponent attributes; an INNER join
 silently drops them.

   Sheet          Opp code  Rows  Cause
   -------------  --------  ----  ---------------------------------------------
   Season Games   ATH         10  The Athletics' current Baseball-Reference
                                  code. The lookup sheet still carries the
                                  franchise under the legacy code OAK.
                                  Affects 2025 rows only.
   PS Games       CWS          4  Chicago White Sox coded "CWS" here, but the
                                  lookup sheet uses "CHW". 2021 Astros ALDS.
   PS Games       BRA          6  Atlanta Braves coded "BRA" here, but the
                                  lookup sheet (and every other sheet) uses
                                  "ATL". 2021 World Series, Astros' rows.

 Related: the PS Games "Tm" column also codes the 2021 Braves as "BRA" on all
 16 of their postseason rows, while WS Teams.Tm ID and Season Games.Tm both use
 "ATL". Any code-based join between PS Games.Tm and another sheet will miss
 those 16 rows. This does not affect the documented model, which joins on
 "Unique", not on team codes.

 Fix: standardise on one code set. Either add an "ATH" row to the lookup (or
 rename OAK to ATH) and change "CWS" to "CHW" and "BRA" to "ATL" in PS Games.

--------------------------------------------------------------------------------
 6.2  Date columns are inconsistent between sheets and mixed within one
--------------------------------------------------------------------------------
 Three separate problems:

 a) "Game Date" has a different data type in each game sheet.
      Season Games : TEXT, format M/D/YYYY  (e.g. "3/20/2024") - all 1,619 rows
      PS Games     : a real Excel DATE                         - all 161 rows
    Any tool reading both sheets will type them differently. Parse the Season
    Games column to a date before using it.

 b) "Date Calc" (Season Games) is mixed-type and intentionally denormalised.
    It exists to overlay all five seasons on one calendar axis, so the year is
    deliberately discarded:
      2021-2024 rows (1,295) : a real date carrying the game's month and day but
                               with the year FORCED TO 2025.
      2025 rows        (324) : TEXT strings such as "Apr-1", "Mar-18", "Sep-9"
                               with no year component at all (173 distinct).
    Do not treat this column as a date, and never use it to derive the season -
    use "Year" or "Game Date". It is a plotting helper only and can be dropped
    from any analytical copy of the data.

 c) "Time" (Season Games) is a DURATION stored as an Excel time value, not a
    first-pitch time. 03:05 means the game lasted 3 hours 5 minutes.

--------------------------------------------------------------------------------
 6.3  "League Champion" is wrong on 161 rows of Season Games
--------------------------------------------------------------------------------
 In Season Games, the denormalized "League Champion" column reads "Runner-Up"
 for the 2025 Dodgers on 161 of their 162 rows. Only Gm# 1 (3/18/2025) reads
 "Champion". The 2025 Dodgers won the World Series, so "Champion" is correct
 and the other 161 rows are wrong - this looks like a fill-down that was not
 completed after the 2025 result was known.

 The join key ("Unique" = "2025_Champion_Dodgers") is correct on all 162 rows,
 and so is the hub, so the published Tableau workbook is unaffected: it reads
 League Champion from the hub table, not from Season Games.

 The same columns in PS Games were checked and are correct on all 161 rows.
 Batting, Pitching and Fielding Year values match the hub on every row.

 >> RECOMMENDATION: Because the hub is authoritative and the copies are not,
    drop the five denormalized columns (League Champion, League, Team Name,
    Team Location, Team Name Short) from Season Games and PS Games in any
    cleaned release, and source them from WS Teams via the join. That removes
    this class of error entirely.

--------------------------------------------------------------------------------
 6.4  Two defects in PS Games "Series Standings"
--------------------------------------------------------------------------------
 a) Five rows hold the NUMBER 0 instead of the text "0 - 5" - the 2024 Yankees'
    World Series rows. Excel appears to have evaluated the entry as arithmetic.
    This is why the column has a mixed data type.

 b) Seven rows read "4 -3" (no space before the 3) instead of "4 - 3" - the
    2025 World Series rows for both the Dodgers and the Blue Jays. Any code
    that parses this column by splitting on " - " will fail on them.

 The equivalent running columns (W - L_S, W_S, L_S) are correct on these rows,
 so the series results can be recovered from the last game of each series.

--------------------------------------------------------------------------------
 6.5  PS Games: 16 rows where W/L disagrees with the score
--------------------------------------------------------------------------------
 This is the most significant accuracy issue in the file. In 16 of the 161
 postseason rows the "W/L" flag and the R / RA columns contradict each other.

 By comparison, Season Games is completely clean: all 1,619 rows have W/L
 consistent with R vs RA, and every team's final cumulative W-L matches a tally
 of its game results.

 Two distinct patterns:

 A) Five rows where R equals RA - an impossible tied result, so R or RA is
    wrong on these rows:
       2021 Braves       Division Series G1  vs MIL   R=1  RA=1   W/L=L
       2022 Phillies     Division Series G2  vs ATL   R=0  RA=0   W/L=L
       2022 Phillies     LCS G2              vs SDP   R=5  RA=5   W/L=L
       2023 Diamondbacks LCS G1              vs PHI   R=3  RA=3   W/L=L
       2023 Diamondbacks LCS G5              vs PHI   R=6  RA=6   W/L=L

 B) Eleven rows where the team with more runs is marked as the loser, or vice
    versa. A pairwise cross-check of the 29 World Series games (each present
    twice, once per team) shows that R and RA ALWAYS mirror correctly between
    the two rows of a game - so the scores are internally consistent and it is
    the W/L flag that is unreliable:

       2021 World Series G5    - W/L inverted on BOTH teams' rows
                                 (Braves row: R=9 RA=5 marked L;
                                  Astros row: R=5 RA=9 marked W)
       2023 World Series G1-G5 - the Diamondbacks' five rows all read "W",
                                 duplicating the Rangers' outcomes. The
                                 Rangers' own rows are correct.
       2024 LCS G5             - Dodgers row reads W with R=6 RA=12
       2024 LCS G3             - Yankees row reads W with R=5 RA=7
       2024 World Series G4    - W/L inverted on both teams' rows
                                 (Dodgers R=4 RA=11 marked W;
                                  Yankees R=11 RA=4 marked L)

 Practical guidance: for postseason win/loss analysis, DERIVE the result from
 the score - (R > RA) - rather than trusting the W/L column, or correct the 16
 rows above before publishing. The 2025 rows are clean.

--------------------------------------------------------------------------------
 6.6  Excel auto-converted four position codes into dates
--------------------------------------------------------------------------------
 The detailed position strings use Baseball-Reference notation in which a value
 can look like a date to Excel. Two rows in Batting Stats column 34 ("Pos",
 the second one) and two rows in Fielding Stats column 30 ("Pos") have been
 stored as datetime values instead of text.

 Additionally, many values in these columns are pure digit strings (e.g. "35",
 "64") and have been stored as NUMBERS: 57 such rows in Batting Stats and 154
 in Fielding Stats. The column therefore has a mixed type overall.

 Fix: import these columns as text, and re-enter the four date-converted cells.

--------------------------------------------------------------------------------
 6.7  "Player-additional" is incomplete
--------------------------------------------------------------------------------
 The Baseball-Reference player ID is the only stable identifier for a player in
 this dataset (names are not unique and change spelling). It has two gaps:

   - NOT POPULATED for either 2025 team in Batting Stats (48 rows, including
     the 2 Team Totals rows) or Pitching Stats (80 rows). The 2025 seasons were
     evidently added from a source or export that omitted the ID.
   - Holds the SENTINEL VALUE -9999 on the Team Totals rows for 2021-2024:
     8 rows each in Batting, Pitching and Fielding Stats. Treat -9999 as null.

 Because of this, do not use Player-additional as a join key across the whole
 dataset. Within a single team-season, "Unique + Player" is a verified unique
 key in all three statistics sheets and is the safer choice.

--------------------------------------------------------------------------------
 6.8  Fielding Stats stops at 2024
--------------------------------------------------------------------------------
 Fielding Stats contains 8 of the 10 team-seasons. Both 2025 teams - the
 Dodgers and the Blue Jays - have zero rows. Any join from the hub to this
 sheet must be an outer join, and any year-over-year fielding comparison should
 be labelled as covering 2021-2024 only.

--------------------------------------------------------------------------------
 6.9  Smaller notes
--------------------------------------------------------------------------------
  - Season Games "W/L" has four values, not two: W, L, W-wo, L-wo. Test with
    "starts with W" rather than "= W", or 70 walk-off wins will be missed.
  - Season Games "Z2" uses a BLANK to mean "home game" (809 rows). A blank here
    is data, not a missing value - do not drop those rows.
  - Season Games "GB" mixes text ("up 1.5", "Tied") with numbers. Parse it; do
    not aggregate it.
  - Season Games "Z1" is a scrape artifact containing only the word "boxscore"
    on every row and can be dropped.
  - Pitching Stats "Pos" (SP/RP/CL) is populated on only 109 of 342 rows. It is
    an author annotation, not a complete Baseball-Reference column.
  - Pitching "IP" and Fielding "Inn" use the baseball thirds convention (x.1 =
    one third, x.2 = two thirds). Convert to outs before doing arithmetic.
  - Extreme-looking values in Batting and Pitching (ERA of 81.00, OPS+ of -100,
    Rbat+ of -358) are genuine: they belong to players with a handful of plate
    appearances or a fraction of an inning. They are not errors, but they will
    distort unweighted averages - weight by PA or IP.
  - The 2021 Braves played 161 regular-season games rather than 162. This is
    correct, not a missing row.
  - "Opponite" is a consistent misspelling of "opponent" in the sheet name and
    in five column names. Preserved deliberately to stay in sync with the
    published Tableau workbook.

================================================================================
 8. USING THE DATA
================================================================================

 Recommended reading order for a newcomer
 ----------------------------------------
   1. Load "WS Teams" first - 10 rows tell you the entire scope.
   2. Join "Season Games" to it on Unique for the regular-season story.
   3. Join "PS Games" to it on Unique for the postseason story.
   4. Attach "Team Name Opponite" separately to each game sheet on Opp.
   5. Treat "Batting Stats" / "Pitching Stats" / "Fielding Stats" as a separate
      grain - aggregate them to Unique before combining with anything else.

 Worked examples
 ---------------
   Regular-season win rate per team-season:
       group Season Games by Unique
       wins = count of rows where W/L starts with "W"
       rate = wins / count of rows

   Home vs away win rate:
       split Season Games on Z2 ("@" = away, blank = home), then as above.

   Day vs night win rate:
       split Season Games on D/N.

   Postseason run differential by round:
       group PS Games by Unique and Series, sum(R) - sum(RA).
       Order rounds with "Series #" descending for chronological order.

   Team home-run total for a season:
       filter Batting Stats to Player <> "Team Totals", then sum HR by Unique.
       (Or read the "Team Totals" row directly - but never do both.)

 Companion files in this data package
 ------------------------------------
 "Baseball Teams Logos.zip" ships alongside this workbook. It contains 30
 transparent PNG logos, one per MLB club, at roughly 905 px on the longest edge
 (~3.5 MB unzipped) - the shape images used by the Tableau visualization.
 Filenames are not standardized and no column in this dataset maps to them
 directly, so a small filename-to-team lookup is needed to join them
 programmatically.
